# Reseller delivery and trial UX

New deliveries use escaped Telegram HTML with a complete VLESS URI in a preformatted block. Usage capabilities appear only in the private status button, not in message text. A CopyTextButton is included when the complete URI fits Telegram’s 256-character limit; longer URIs remain complete in the code block. URI fragments use a short account reference to keep normal REALITY configurations copyable. Historical sent messages are not edited.

Every new trial has 1,000,000,000 bytes and 1,800 seconds. Legacy pending confirmations with a null quota are accepted but receive this server-side cap. Separate requests create separate identities; retries remain idempotent. Migration 0006 caps older trials without resetting usage, expiry or terminal states.

Seller flows accept Persian, Arabic and ASCII digits, provide cancellation and request-status navigation, and paginate accounts with ownership checks. Account details show recorded consumption and report time. Administrators see assigned server purposes and must confirm account revocation.

Release: run sales-bot tests, typecheck and build; apply migration 0006; deploy the Worker preserving existing bindings, schedules and secrets. No node reinstall is needed. Verify a fresh delivery in Telegram; old forwarded messages retain their previous appearance.

Full UI pass: role-aware home with active-account summary and help; administrator seller directory; quick quota/day choices and backward editing; authenticated resend of the original customer delivery without token rotation. Mobile pages use the same dark palette, visible focus styles, larger touch targets and status announcements. Consumption remains based on dated reports rather than a claimed realtime connection count. No credentials, node purposes or working VPN transport are changed by this release.

Server selection and capacity: migration 0007 adds max_accounts (default 100, allowed 1–10,000). Enrollment accepts this limit and administrators can change existing limits in the server menu. The picker offers fresh, healthy quota-v2 servers and shows remaining slots. Preparing accounts and active accounts with remaining time/volume reserve a slot. Expired, depleted and terminal accounts do not. INSERT…SELECT enforces the count and limit atomically; request replay returns the existing account. Legacy confirmations retain default server compatibility. Lowering a limit never deletes accounts, but prevents new issuance until capacity is available. The limit is an issuance limit, not a speed guarantee. Apply migration 0007 before deploying the Worker; no node update is required.

Seller invitations: administrators create a 24-hour, single-recipient Telegram start link from the seller directory. The payload contains a 128-bit invitation capability; only its hash is stored in the invitation table. The delivery outbox retains the original link for idempotent Telegram retries. Claiming and reseller activation are atomic. A consumed invite cannot activate a second recipient or reenable its recipient after an administrator disables them. Migration 0008 must precede Worker deployment. The bot discovers its own username with getMe and caches it in settings; bot tokens are never included in invitation URLs.

Enrollment audit (2026-10-16): a real probe job was leased and completed by sales-runner-1 in approximately 16 seconds. Runner tests: 31 passed. Installation completion now remains `verifying` in the administrator job view until fresh node health and exact revision ACK are present. This is control-plane readiness, not proof of Internet reachability from a customer's mobile operator. The installer does not modify provider security groups or host firewalls. SSH credentials alone cannot authorize AWS security-group changes. A fresh-server installation and client data-plane test remain required before claiming fully automatic end-to-end acceptance.
